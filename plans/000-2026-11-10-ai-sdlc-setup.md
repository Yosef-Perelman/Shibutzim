## Goal

Turn the one-off planning brief into the permanent, file-based working environment every later session starts
from: an instructions index for agents, written rules, a roadmap, guardrails that limit what an agent can break,
narrow-role subagents, and a skill that drafts the next plan. After this plan, `CLAUDE.md → AGENTS.md → ROADMAP.md`
must be enough to continue the project from a cold start.

## Scope

### In

1. `AGENTS.md` – the index: project summary in five lines, task → doc map, guardrails, common commands,
   the reply canary, the plan-to-plan workflow, the session-start routine.
2. `CLAUDE.md` – one line: refer to `AGENTS.md`.
3. `docs/rules/` – nine rule files: `planning-rules.md`, `coding-rules.md`, `database-rules.md`,
   `error-handling-rules.md`, `naming-rules.md`, `style-rules.md`, `testing-rules.md`, `ui-rules.md`, `git-rules.md`.
4. `plans/ROADMAP.md` – the six plans with status and link; the single source of "what's next".
5. `docs/archive/SHIBUTZIM_BRIEF.md` – the brief moved there unchanged, **kept local only**: `.gitignore`
   excludes it, so it never reaches the public remote (amended on approval, see below).
6. `.claude/settings.json` – permissions: allow pytest, ruff, alembic, uv, safe git; deny reading or editing
   `.env` files, `git push --force`, `rm -rf`.
7. `.claude/hooks/` – two scripts wired in `settings.json`:
   - `PreToolUse` on `Edit|Write`: block `.env` and `.env.*` (except `.env.example`) and any **existing** file under
     `server/alembic/versions/`.
   - `PostToolUse` on `Edit|Write` of `*.py`: run `ruff format` and `ruff check --fix` on the file, then
     `pytest -q -x` in `server/`; print failures back to the agent. No-op when `server/pyproject.toml` or the tools
     don't exist yet.
8. `.claude/agents/` – `backend.md`, `frontend.md`, `qa.md`, each with a narrow role, the docs it must load, and
   its tool list.
9. `.claude/skills/new-plan/SKILL.md` – reads `ROADMAP.md`, takes the next `todo` plan, creates
   `plans/NNN-YYYY-MM-DD-name.md` from the planning-rules template, sets the roadmap row to `in progress`, and stops
   for approval.
10. `.gitignore` – Python, Node, `.env`, editor and OS files.

### Out

- Any application code, `pyproject.toml`, Docker Compose, dependencies (plan 001).
- The `add-pay-rule` and `debug-schedule` skills (plans 001 and 002).
- README rewrite (final deliverable; a short "work in progress" note is enough now).
- CI workflows (plan 005).

## Assumptions

- Claude Code is the primary agent; `AGENTS.md` is written so any agent can follow it, `CLAUDE.md` only redirects.
- Hooks are small Python 3 scripts (macOS ships `python3`; no `jq` dependency). They read the hook JSON from stdin and
  exit with code 2 to block.
- Package manager for the server will be **uv** (decided here only so far as the permission allowlist needs it;
  confirmed again in plan 001).
- The docs trio already exists (created and committed before this plan by explicit approval, as decided with Yosef).

## Steps

Each step is one commit, in this order.

1. **Rules** – write the nine files in `docs/rules/`. Key contents:
   - *planning*: file naming, metadata table, required sections (Goal, Scope in/out, Assumptions, Steps,
     Validation, Rollback, Open questions with suggested answers), status lifecycle
     `draft → approved → in progress → done`, the closing "what changed vs. plan" note, one plan at a time.
   - *coding*: layer rules from architecture.md §3, pure modules, type hints everywhere, no business logic in
     routers, services take `current_user`, small functions, no dead code, dependencies only via an approved plan.
   - *database*: SQLAlchemy 2 declarative models, Alembic one migration per change, never edit an existing migration,
     UTC `timestamptz`, `numeric(10,2)` for money, explicit unique constraints and indexes, no raw SQL outside
     repositories.
   - *error-handling*: typed domain errors, one handler, the `{error:{code,message}}` shape, error-code catalogue,
     never leak internals, validate at the boundary.
   - *naming*: glossary.md §1 restated as rules, plus file and test naming.
   - *style*: ruff (format + lint) for Python, Prettier + ESLint for TypeScript, line length, import order,
     docstrings only where they add information.
   - *testing*: tests first for pure modules, the mandatory pay and scheduler matrices, test naming
     `test_<unit>_<case>`, API tests via the FastAPI test client, evals for the assistant, no test touches a real
     LLM.
   - *ui*: mobile-first for employee screens, MobX store per domain, components observe and never fetch,
     typed API client, loading / empty / error states for every list, Mantine components over custom CSS.
   - *git*: Conventional Commits (`docs:`, `plan:`, `test:`, `feat:`, `fix:`, `chore:`), commit order within a
     plan is plan → tests → code, plan 000 on `main`, from plan 001 a branch per plan merged with a merge commit
     (no squash) so the trail stays visible, never force-push, never commit `.env`.
2. **ROADMAP** – `plans/ROADMAP.md` with the six plans; 000 `in progress`, the rest `todo`.
3. **AGENTS.md + CLAUDE.md** – including:
   - the canary rule (every chat reply starts with `Yosef my king:`; never in files);
   - task → doc map (e.g. "pay change → product-definition §6.1, coding-rules, testing-rules");
   - the plan-to-plan workflow quoted from the brief;
   - the session-start routine: read `ROADMAP.md`, then the current plan, then only the docs the task needs;
   - common commands (to be filled as plans 001+ introduce them).
4. **Archive the brief + `.gitignore`** – add `.gitignore` (ignoring `SHIBUTZIM_BRIEF.md` anywhere), then move
   the brief to `docs/archive/SHIBUTZIM_BRIEF.md`. The brief was never committed, so nothing needs rewriting in
   history. No `docs/archive/README.md` (the folder is local only); drop `archive/` from the layout in
   architecture.md.
5. **Guardrails** – `.claude/settings.json`, `.claude/hooks/pre_edit_guard.py`, `.claude/hooks/post_edit_py.py`.
6. **Subagents** – `.claude/agents/backend.md` (server only; loads architecture, coding, database, error-handling,
   testing rules), `frontend.md` (client only; loads architecture §9, ui, naming, style rules), `qa.md` (reads
   everything; writes only under `server/tests/`, `server/evals/`, `client/src/**/*.test.*`).
7. **Skill** – `.claude/skills/new-plan/SKILL.md` with the procedure above and the plan template inline.
8. **Close** – run the validation below, set this plan to `done` with the "what changed vs. plan" note, update
   `ROADMAP.md`, then use `/new-plan` to draft plan 001 and stop.

## Open questions (each with a suggested answer)

1. **`pytest -q` after every `.py` edit will get slow as the suite grows.** Keep it?
   → *Suggested:* keep it for now with `-x` (stop at first failure) and a 60 s wall clock in the hook. Revisit in
   plan 002 if a run exceeds about 20 s; the fallback is to run only `server/tests/unit` on edit and the full suite
   on commit.
2. **Hard enforcement of the `qa` path scope.** Claude Code agents can restrict *tools*, but a path-scoped write
   restriction per agent may need hook support.
   → *Suggested:* state the scope in `qa.md` and give qa the Edit/Write tools; during step 6 check whether hook
   input exposes the running agent, and if it does, enforce the path scope in `pre_edit_guard.py`. Record the
   outcome in the closing note.
3. **Branching model.** All on `main`, or branch per plan?
   → *Suggested:* plan 000 directly on `main`; from plan 001 a branch per plan (`plan/001-skeleton`) merged with a
   merge commit, no squash, so the plan → tests → code order survives in history. PRs become meaningful when CI
   arrives in plan 005.
4. **Package manager in the allowlist.** `uv` vs `pip` + `venv`?
   → *Suggested:* `uv` (lockfile, fast, one tool for venv and deps). Reconfirmed in plan 001 before anything is
   installed.
5. **Should `.env.example` be excluded from the `.env*` block?**
   → *Suggested:* yes. The hook blocks `.env` and `.env.*` except `.env.example`, and `settings.json` denies
   `Read(./.env)` and `Read(./.env.*)` the same way.
6. **Subagent models.** Pin a model per agent?
   → *Suggested:* no pin in v1; inherit the session model. Pinning is an optimization to revisit when costs or
   speed matter.
7. **Should the plan-status lifecycle include `approved`?**
   → *Suggested:* yes: `draft → approved → in progress → done`. `approved` is the explicit record that the human
   signed off before any code; `in progress` starts at the first implementation commit.

## What changed vs. plan

**Deviations**

- **Brief kept local** (amendment on approval): `.gitignore` excludes `SHIBUTZIM_BRIEF.md` anywhere; the brief lives
  at `docs/archive/` on the local machine only and was never committed. No `docs/archive/README.md`; `archive/` was
  removed from the layout in architecture.md. `.gitignore` therefore moved from step 5 to step 4.
- **`.env` guard also covers the Read tool.** Permission deny rules always win over allow rules, so a `.env.*` deny
  would also block `.env.example`. Settings deny only the concrete names `.env` and `.env.local`; the PreToolUse hook
  enforces the general rule "`.env` and `.env.*` except `.env.example`" for Read, Edit and Write.
- **Open question 2 resolved:** Claude Code supports hooks in subagent frontmatter (active only while that subagent
  runs). The qa write scope is enforced by `.claude/hooks/qa_scope_guard.py` registered in `qa.md`.
- **`CLAUDE.md` imports AGENTS.md** with `@AGENTS.md` instead of only linking it, so the rules load automatically.
- **Hook scripts target Python 3.9**, because the system `python3` is 3.9.6 and the hooks must run before uv
  exists.
- `docs/architecture.md` layout gained `tests/services/` to match testing-rules.
- Plan 000 itself quotes the reply canary when describing AGENTS.md, so the canary grep matches two files; accepted
  (a description, not an instruction).

**Validation results**

- Passed: CLAUDE.md redirect; no broken relative links; all nine rules linked from AGENTS.md; roadmap lists
  000–005; the brief is ignored and no commit touches it; `settings.json` is valid JSON.
- Hooks were tested by piping simulated hook input into each script: 22 of 22 block/allow cases passed
  (`.env` read/edit, `.env.example` allowed, existing vs new migration, relative paths, post-edit no-op paths,
  missing `uv` warning, qa scope including path traversal and lookalike folders).
- `/new-plan` was validated by drafting plan 001 with its procedure.
- **Not yet run:** the live-session checks (hooks firing inside Claude Code, deny rules on `git push --force` /
